# VIP + admin console gaps — backend contract (2026-10)

Owner request (2026-10-23): sell VIP for **real money**, detect who is VIP, show a per-tier picture
frame (web profile avatar, P2P market seller, in-game chat), and drive the in-game VIP commands
through the ArkApi **Permissions** plugin. Plus: the admin console must see everything (orders,
deliveries, audit log, P2P market, site settings, plugin keys, payments).

Conventions are unchanged (`ui-redesign-2026-10.md`): JSON, errors `{ "error": string }` with
400/401/403/404/409, money in THB is a **decimal string** (`"199.00"`), IC amounts are bigint
strings, dates are ISO-8601 UTC, admin lists use the Admin pagination contract
(`page`, `pageSize` snapped to 10/25/50/100, page clamped after count).

## 1. Data model (migration `20261023010000_vip_memberships`, additive, NOT applied yet)

```
VipPackage    { id, key (unique), name, description?, permissionGroup='VIP', tierRank=1 (higher = better),
                frameStyle='vip-gold', badgeLabel='VIP', priceThb Decimal(10,2)=0, durationDays? (null = permanent),
                isActive=false, sortOrder=0, createdAt, updatedAt }
VipMembership { id, userId, packageId, permissionGroup (snapshot), startsAt, expiresAt? (null = permanent),
                status 'active'|'expired'|'revoked', source 'purchase'|'admin'|'legacy',
                paymentIntentId? (UNIQUE), grantedBy?, revokedAt?, revokedBy?, reason?,
                syncStatus 'pending'|'synced'|'failed'|'no_steam'|'unqueued', syncedAt?, createdAt, updatedAt }
PaymentIntent + vipPackageId? ; packageId becomes nullable.
  CHECK payment_intents_kind_check: exactly one of package_id / vip_package_id, and a VIP intent has points_amount = 0.
```

Seed (in the migration): package `vip-30d` "VIP 30 วัน", group `VIP`, 30 days, `vip-gold`, price **0**,
**inactive** — the owner sets a price and activates it in the admin console. A global ChatRank
`{ groupKey: 'VIP', name: 'VIP', color: '#D4AF37', priority: 50 }` is inserted unless one exists.

**One row per grant.** A new grant *chains* per permission **group**: the new row starts at the
later of now / the latest live expiry among the user's live rows of the **same group whose package
tierRank is the same or higher**, and lasts `durationDays`. So `vip-90d` bought while `vip-30d`
(same group, same tier) has 20 days left starts after those 20 days (no paid days lost); a
higher-tier package starts now and overlaps (better frame at once); a lower tier bought while a
higher one runs starts after it. Extend and revoke keep the chain contiguous (see §8).

Derived `state` (API only): `scheduled` (active, startsAt > now) · `active` (effective now) ·
`expired` (status expired, or expiresAt ≤ now) · `revoked`.

**Effective** = `status='active' AND startsAt ≤ now AND (expiresAt IS NULL OR expiresAt > now)`.
A user **holds** a Permissions group while any `active` row of that group has not ended
(scheduled chained rows count, so there is no gap at a renewal boundary).

### VipBadge (public)

```ts
{ tierRank: number; frameStyle: string; label: string }   // or null when not VIP
```

Best effective row: highest `tierRank`, ties → the longer one. Frame keys with CSS in the frontend:
`vip-gold`, `vip-silver`, `vip-diamond`, `vip-emerald`, `vip-ruby`, `vip-amethyst` (backend accepts
any `vip-[a-z0-9-]`; unknown keys render as gold).

### Membership (API shape)

```ts
{
  id, userId,
  user: { id, name, steamId, avatar } | null,
  packageId,
  package: { id, key, name, tierRank, frameStyle, badgeLabel, permissionGroup } | null,
  permissionGroup, startsAt, expiresAt /* null = permanent */,
  status: 'active'|'expired'|'revoked', state: 'scheduled'|'active'|'expired'|'revoked',
  source: 'purchase'|'admin'|'legacy', paymentIntentId, grantedBy, revokedAt, revokedBy, reason,
  createdAt, updatedAt,
  sync: {
    status: 'pending'|'synced'|'failed'|'no_steam'|'unqueued',   // this row's Permissions sync (unqueued = no server row to queue on; re-queued by the scheduler)
    syncedAt, jobId, jobStatus /* DeliveryJob status */, action: 'add'|'remove'|null,
    attempts, lastError, updatedAt                      // latest permission job for (user, group)
  }
}
```

## 3. Payment completion (one path, idempotent)

`fulfillPaidIntent(tx, intent, …)` is the single completion step used by the Stripe webhook,
`POST /payments/verify-session`, and admin slip approval. Every caller first flips the intent
`pending|processing → completed` conditionally inside the same Serializable transaction.

- `vipPackageId` set → `vipService.grantFromPaymentIntent`: create the chained membership
  (`source='purchase'`, `paymentIntentId` UNIQUE → a second grant for one intent is impossible;
  a replay returns the existing row), queue `permission_grant`, then after commit:
  `vip:updated` → user, `admin:vip {action:'granted'}` → admins, AuditLog `vip_purchase_grant`.
  **No wallet call at all.**
- otherwise → the existing IC credit (`walletService.creditUser`, same ledger keys as before).

Webhook result for VIP: `{ accepted: true, credited: false, vipGranted: true, kind: 'vip', intentId }`.
Slip approval result: `{ success, kind: 'vip', creditedPoints: 0, vipMembershipId, transactionId }`.
`GET /admin/payments/pending-slips` rows gain `kind: 'topup'|'vip'` and `vipPackageId`
(`pointsToCredit` is 0 for VIP). Refunds of real money are done at the provider; then an admin
revokes the membership (`POST /admin/vip/memberships/:id/revoke`).

**Slip review is website-admin only.** `GET /admin/payments/pending-slips`,
`POST /admin/payments/approve/:id` and `POST /admin/payments/reject/:id` use `requireWebsiteAdmin`
(role `admin` | `root`; never `server_admin` or the legacy `isAdmin` flag). Approving a slip whose
intent belongs to the approver is `403` (four-eyes: nobody approves their own VIP / IC slip).

**IC top-up slips are server-priced.** `POST /payments/slips { packageId, transferBank?, transferRef?, slipImageUrl?, notes? }`
requires an active, priced `PaymentPackage` (by id or slug; `404` otherwise, no fallback package).
`amountThb = package.priceThb`, `pointsAmount = points + bonusPoints`, `packageName = package.name`;
client `amountThb` / `pointsToCredit` / `packageName` are ignored. `slipImageUrl` must be
`https://…` or `/path` (400 otherwise); one of `slipImageUrl` / `transferRef` is required. The
intent `reference` is server-generated; the payer's reference is `metadata.transferRef`.
Before deploying, audit pending `bank_slip` top-up intents whose `points_amount` /
`amount_thb` differ from their package (created by the old client-priced endpoint).

## 4. Permissions plugin sync (DeliveryJob)

Every membership change queues one job (existing `DeliveryJob` table):

| field | value |
|---|---|
| `deliveryType` | `permission_grant` (add) / `permission_revoke` (remove) |
| `referenceId` | `vip:<userId>:<group>` |
| `playerSteamId` | the user's linked Steam ID (no Steam link → no job, membership `syncStatus='no_steam'`) |
| `serverId` | FK host only (a capable, non-drained, recently seen server); reassigned to the claimer |
| `payload` | `{ schemaVersion: 1, steamId, group, action: 'add'|'remove', expiresAt? }` — exactly these keys; `expiresAt` (ISO) only on `add` with an end date, **informational** |
| `payloadHash` | sha256 of `JSON.stringify(payload)` (same rule as other jobs) |

**Claim (`POST /plugin/deliveries/claim`, unchanged request/response).** In addition to its own
jobs, a server receives permission jobs from ANY server when it is `isActive`, **not draining**,
and its heartbeat advertises capability **`permissions.group.v1`**. Per key
`(referenceId, steamId)` only the newest job is handed out; older pending jobs are superseded at
enqueue time (`status=completed`, `receiptId='superseded:<newer id>'`), older expired leases are
superseded at claim time, and a key with a live lease elsewhere is skipped. Servers without the
capability never receive these jobs (their own item/dino jobs are unaffected).

**Plugin contract (permissions.group.v1)** — HeartShop `src/PermissionSync.*` + `src/PermissionsBridge.*`
(Permissions is resolved at runtime by export name, never linked; reconciled with the code 2026-10-23):
- The player does **not** need to be online and the job does **not** belong to the server's map.
  Never `release` a permission job because the player is offline. A server releases (no attempt
  consumed) only when Permissions is not loaded, the group is outside its optional
  `HeartShop.Permissions.AllowedGroups`, or its journal cannot be written.
- Payload is validated strictly: `schemaVersion` 1, `steamId` = SteamID64 equal to the job's
  `playerSteamId`, `action` matching the job type, group `[A-Za-z0-9_.+-]{1,64}`; `Admins` /
  `Default` are refused (the backend also rejects them as a package group).
- `add` **with** `expiresAt`: `RemovePlayerFromGroup` + `RemovePlayerFromTimedGroup` +
  `AddPlayerToTimedGroup(remaining seconds)`. The in-game group therefore ends at `expiresAt`
  even if the web scheduler is down, and a re-run lands on the same absolute end (Permissions
  ADDS to a running timer, hence the reset). `expiresAt` is the **group hold** (latest end over
  every live row of that group, chained renewals included), not one row's end. An `add` whose
  `expiresAt` has already passed is a no-op success. Without timed-group exports it falls back
  to a permanent add and the web `remove` ends it.
- `add` **without** `expiresAt` (permanent): `AddPlayerToGroup`.
- `remove`: `RemovePlayerFromTimedGroup` **and** `RemovePlayerFromGroup` (legacy timed VIPs too).
- "Already in group" / "not in group" = success; after an add `IsPlayerInGroup` must be true.
- Because adds are timed, the backend re-queues an `add` with the new hold whenever it changes:
  purchase / grant / extend (longer), and **revoke of one row while another still holds the
  group** when that shortens the hold. Expiry of a row never shortens the hold (it already ended).
- Then `complete` with the usual receipt (`playerSteamId` = payload `steamId`, same `payloadHash`).
  A real Permissions error → `fail` (normal backoff / dead-letter). Journaled; a completed job is
  only re-acknowledged, a changed payload for the same job id fails.
- One online server is enough: the group store is the cluster-shared MySQL.

**In-game `/vip` (and `/iris vip`).** `GET /api/plugin/player/:steamId/vip` (signed, plugin
gateway, not server-scoped; `400` for a non-SteamID64) →
`{ linked, steamLinked, isVip, vip: VipBadge|null, active: { state, packageName, label, tierRank, permissionGroup, expiresAt } | null, groups: [{ group, expiresAt }] }`.
Unknown / unlinked Steam IDs answer `200 { linked: false, isVip: false, vip: null, active: null, groups: [] }`.

Completion of the **newest** job for `(referenceId, playerSteamId)` marks the user's matching
memberships `syncStatus='synced'` (add → active rows, remove → expired/revoked rows); a dead-letter
of the newest job marks them `failed` whatever they showed before and emits
`admin:vip {action:'sync', status:'failed'}`. An older job finishing while a newer job for the key
is pending/leased changes nothing.

**No server row.** When no server row can host a job, nothing is queued, the affected `pending`
rows become `syncStatus='unqueued'` and `admin:vip {action:'sync', status:'unqueued'}` is emitted.
Each scheduler tick (§5) re-queues up to 20 such users (a resync) once a server row exists.

**Permissions cache affinity.** Permissions V2 answers group reads from a per-server cache that
reloads from MySQL every `ClusterSyncTime` (default 60 s, minimum 20 s). A follow-up job for the
same `(referenceId, playerSteamId)` is therefore handed only to the server that completed the
previous job for that key while that completion is younger than `ClusterSyncTime + 30 s`
(`PERMISSIONS_CLUSTER_SYNC_SECONDS`, default 60). Other servers skip the key until the window has
passed (a superseded lease does not pin a key). Without this, a revoke run on a stale server reports
"not in group" (counted as success) while MySQL still holds the timed VIP. The completing server
and time are the job's `serverId` / `updatedAt` in `/admin/deliveries`.
`POST /admin/deliveries/:id/retry` accepts permission jobs only while no newer job exists for the
key (else 409 "use VIP resync"). Companion endpoints (`/plugin/player/:steamId/*`, wallet events)
ignore permission jobs, so they never associate a player with the server that ran them.

Optional, not built: heartbeat/claim reporting group-membership drift.

**In-game chat rank.** Reuses Chat Ranks: the seeded `VIP` rank is in `GET /chat/plugin/config`
`ranks`. Three directions:
- game → web/Discord: `POST /chat/plugin/messages` adds the VIP groups the web knows for the
  sender's Steam ID to the reported `playerGroups`, so a VIP gets the rank even before the group
  sync lands.
- web/Discord → game: `GET /chat/plugin/messages` items gain additive `vip: VipBadge|null` and
  `rankTag: string|null` (the badge label, web senders only). HeartShop prints
  `[Web] [VIP] Name: text`.
- native in-game global chat: HeartShop loads `ranks` every 5 minutes and, for a player whose
  Permissions groups match a rank (highest `priority` wins), re-sends the line to every player as
  `[VIP] CharacterName` and suppresses the default line (ArkApi chat callback; chat commands and
  spam never reach it), then forwards it to cross-chat itself. Config
  `HeartShop.Vip.ChatRankPrefix` (default `true`); set it to `false` when another plugin already
  prefixes chat by Permissions group.
Creating/renaming a package group creates a global rank for that group if none exists.

## 5. Expiry

`vipExpiryScheduler` (web process, every 60 s, Redis lock `lock:vip:expiry`; never runs without
the lock, a Redis outage only delays expiry). Each due row (`active`, `expiresAt ≤ now`) flips to
`expired` in its own transaction; if no live row keeps the group a `permission_revoke` is queued.
Emits `admin:vip {action:'expired'}` and `vip:updated {reason:'expired'}`; AuditLog `vip_expire`.
The same tick then re-queues `syncStatus='unqueued'` memberships (up to 20 users, resync) when a
server row exists (`vipService.requeueUnqueued`). `GET /admin/vip/summary` counts `unqueued` in
`sync.pending`.
Env: `VIP_EXPIRY_INTERVAL_MS`, `VIP_EXPIRY_ENABLED=false` to disable.

Steam link changes: `POST /auth/link-steam` and `/auth/unlink-steam` queue a remove for the old
Steam ID and re-sync the new one (best effort, AuditLog `vip_steam_link_changed`).

Rules: activating a package (or creating it active) requires `priceThb > 0` (409). `permissionGroup` may not be `Admins` / `Default` (400). `reason` is
3–500 chars. Extend applies only to active/scheduled rows with an end date (permanent / ended →
409) and shifts later chained rows of the same **permission group** (startsAt ≥ the row's old end)
by the same days. Revoke of a non-active row → 409. Revoking a row with an end date moves later
chained rows of the same group (startsAt ≥ the revoked row's end) **earlier** by the revoked row's
remaining span (`end − max(start, now)`), so a revoked head of a chain never leaves a gap where the
web shows "not VIP" while the in-game timed group still runs. The group is removed only when no
other live row keeps it, otherwise an `add` with the new (shorter) hold is queued when the hold
changed (`permissionJob` is then that add). Audit `vip_admin_revoke` records `shiftedLaterRows`.
Grants chain like purchases. `permissionJob` = `{ queued, jobId, reason?: 'no_steam'|'no_server' }`.

## 9. Deploy checklist

1. DB backup, then `prisma migrate deploy` inside the Docker network (adds 2 tables, 1 column, constraints, seeds).
2. Rebuild backend + plugin-gateway (same image).
3. Owner: set the `vip-30d` price, then activate it (`PUT /admin/vip/packages/vippkg_vip_30d`).
4. Plugin: ship a build that advertises `permissions.group.v1` on at least one non-drained server,
   otherwise VIP rows stay `syncStatus='pending'` (the web badge works regardless).
   If the plugin's Permissions `ClusterSyncTime` is not 60 s, set `PERMISSIONS_CLUSTER_SYNC_SECONDS`
   on plugin-gateway to the same value.
5. Stripe: `STRIPE_CHECKOUT_ORIGIN` must serve `/vip` (frontend page) for the return URL.
